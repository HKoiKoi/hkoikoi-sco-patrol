# SCO 순찰 일지 MVP PRD

## 🎯 핵심 정보

**목적**: 30분 간격 순찰 업무를 스마트폰/태블릿에서 최소 터치로 기록하고, 결과를 구글 스프레드시트에 한 줄씩 붙여넣을 수 있게 한다.
**사용자**: SCO 관리형 독서실에서 순찰을 수행하는 매니저와 이를 관리하는 관리자. 승인 전 가입자(`pending`)와 비로그인 방문자는 일지 조회만 가능하다.

## 👥 역할과 권한

| 구분                | 일지 조회 | 순찰 기록 작성      | 본인 기록 수정·삭제 | 타인 기록 수정·삭제 | 퀵 태그 관리 |
| ------------------- | --------- | ------------------- | ------------------- | ------------------- | ------------ |
| 비로그인            | ✅        | ❌ (로그인 안내)    | ❌                  | ❌                  | ❌           |
| `pending` (승인 전) | ✅        | ❌ (승인 대기 안내) | ❌                  | ❌                  | ❌           |
| `manager` (매니저)  | ✅        | ✅                  | ✅                  | ❌                  | ❌           |
| `admin` (관리자)    | ✅        | ✅                  | ✅                  | ✅                  | ✅           |

- 신규 가입자(Google, 이메일 모두)는 `pending`으로 시작하며, 매니저/관리자 승격은 Supabase 대시보드에서 수동 처리한다. 첫 관리자도 대시보드에서 직접 지정한다.
- 매니저가 `pending`으로 강등되면 이후 작성·수정·삭제가 모두 막힌다(과거 기록과 작성자 이름 표시는 유지).
- 일지 조회는 로그인 없이 열람 가능하다. 즉 URL을 아는 누구나 좌석 번호·메모·작성자 이름을 볼 수 있다 (운영 정책으로 수용).

## 🚶 사용자 여정

```
1. 일지 조회 페이지 (/logs) — 앱 기본 진입, 로그인 없이 열람 가능
   - 영업일 기준 전원의 순찰 타임라인 열람, 날짜 이동
   ↓ [순찰 기록 작성] 버튼 탭

   ├─ pending → "관리자 승인이 완료되지 않아 작성할 수 없습니다" 메시지 (이동 없음)
   └─ 매니저/관리자 → 2번

   [로그인] → 로그인 페이지 → 성공 시 일지 조회 페이지로 복귀

2. 순찰 기록 페이지 (/protected/patrol, 매니저·관리자)
   - 서버에 본인 초안이 있으면 자동 복원 (기기 무관)
   - 좌석/퀵 태그/메모 입력 → 약 1초 후 자동 저장
   ↓ [순찰 완료] 탭 (서버 시각 자동 기록, 초안 초기화, 같은 페이지에서 바로 다음 순찰 입력 상태로 돌아가 2번 반복)
   [일지 조회 메뉴] → 1번

3. 일지 조회 페이지에서 항목별 선택
   [복사] → 해당 기록 한 줄 문자열 클립보드 복사 → 구글 시트에 붙여넣기 (누구나)
   [자리비움 이동/삭제] → 확정 기록 갱신 (본인 기록 또는 관리자)
   [수정/삭제] → 본인 기록 또는 (관리자) 타인 기록

5. 퀵 태그 관리 페이지 (/protected/admin/tags, 관리자 전용)
   - 태그 추가/수정/순서 변경/노출 전환/삭제 → 순찰 기록 페이지 버튼에 반영

6. 로그아웃 → 일지 조회 페이지
   (비로그인 상태로 /protected/* 접근 시 로그인 페이지로 자동 리디렉션,
    pending이 작성·관리 페이지에 직접 접근하면 일지 조회 페이지로 돌려보내고 승인 대기 메시지 표시)
```

## 📋 복사 문구 형식 (F06)

순수 함수 `lib/patrol-format.ts`가 생성한다. 항상 개행·탭 없는 한 줄이다.

```
HH:mm 순찰 → 완료[ (상세)]
상세 = 메모 줄들을 ", "로 연결 [+ ", " + 졸음/딴짓 번호들을 ", "로 연결 + "번 졸아서 깨움"]
```

- 메모를 줄 단위로 나눠(`\r\n`, `\n` 모두 줄바꿈) 각 줄의 앞뒤 공백을 제거하고 빈 줄은 버린 뒤 ", "로 연결한다. 탭 문자와 전각 공백은 일반 공백 한 칸으로 바꾼다.
- 졸음/딴짓 번호는 오름차순으로 정렬해 표기한다.
- 졸음/딴짓 번호가 없으면 해당 부분 생략, 메모도 졸음/딴짓도 없으면 괄호 전체 생략.
- 메모가 없고 졸음/딴짓만 있으면 앞 구분자 없이 `(23번 졸아서 깨움)`.
- 스탠딩·카페존·자리비움 번호는 포함하지 않는다. 퀵 태그는 메모 텍스트로만 반영된다.

### 복사 동작

- 복사 버튼은 일지 조회 페이지의 기록 항목에만 둔다. 순찰 기록 페이지에는 두지 않는다.
- 클릭 핸들러 안에서 **`await` 없이 즉시** `navigator.clipboard.writeText`를 호출한다 (HTTPS 필수, 사용자 탭 직후에만 허용되는 브라우저가 있음). 완료 처리를 기다린 뒤 자동 복사하는 방식은 쓰지 않는다.
- 복사가 실패하거나 지원되지 않으면 문구를 전체 선택된 입력란으로 보여 직접 복사하게 한다.
- 개발 중 실기기 테스트는 `http://192.168.x.x` 접속에서는 복사가 막히므로 HTTPS 터널을 사용한다.

## 🔁 자동 저장 규칙 (F05, F07)

- 저장은 `save_patrol_draft(base_revision, 내용)` RPC로만 한다(테이블 직접 쓰기 불가). 초안에는 `revision`이 있고, `base_revision`이 서버와 다르면 충돌로 응답한다.
  - 초안 행이 아직 없는 첫 저장은 `base_revision = 0`일 때만 내용을 저장한다(그 외는 충돌). 충돌 응답에도 `server_draft`를 담기 위해 먼저 빈 초안 행(`revision` 0)을 만들고 잠근다. 초안 행은 삭제하지 않으므로 `revision`은 한 번도 재사용되지 않는다.
  - 서버는 값을 다시 검증한다: 좌석 번호는 양의 정수·카테고리 내 중복 제거, 메모는 2,000자 이하.
  - 충돌 시 로컬에 저장 안 된 입력이 있으면 "다른 기기에서 수정됨, 어느 쪽을 쓸까요?"를 묻고, 서버 초안이 비어 있으면(정리·완료로 초기화된 경우) 로컬 입력을 새 `revision` 기준으로 다시 저장한다.
- 기기당 저장 요청은 동시에 1개만 보내고, 대기 중 변경은 최신 상태 하나로 합친다.
- `updated_at`과 초안의 영업일은 서버(DB) 시각으로만 기록한다. 클라이언트 시계는 사용하지 않는다. 저장 성공 응답에 서버 `updated_at`을 담아 "저장됨 HH:mm"을 재조회 없이 표시한다.
- 서버가 저장을 거절한 경우(권한·검증·DB 오류)는 네트워크 실패(오프라인)와 구분해 `error` 상태로 표시하고 로컬 백업을 유지한다. 자동 재시도는 하지 않으며, 다음 입력이 있을 때 다시 저장한다.
- 탭 포커스 복귀 시 로컬에 저장 안 된 변경이 있거나 저장 중이면 서버 초안으로 덮어쓰지 않는다. 저장 안 된 입력이 없는 상태(`clean`·`saved`)에서만 서버 `revision`이 더 클 때 교체한다.
- 네트워크 실패 시 `localStorage`(키 `draft:{user_id}`, 값 `{revision, savedAt, payload}`)에 임시 백업한다. 온라인 복귀 시 `base_revision`과 함께 재전송하고, 충돌하면 "다른 기기에서 수정됨, 어느 쪽을 쓸까요?"를 묻는다. 완료 성공 또는 로그아웃 시 백업을 삭제한다(공용 태블릿 보호).
- 순찰 완료 전 클라이언트는 대기 중인 저장을 즉시 보내고 끝나기를 기다린다. 완료 RPC(`complete_patrol(client_request_id, expected_revision)`)는 클라이언트가 보낸 값이 아니라 **서버에 저장된 초안**을 사용하며, 완료 후 초안을 삭제하지 않고 빈 값과 `revision + 1`로 초기화해 늦게 도착한 옛 저장을 거부한다.
- 완료 RPC의 처리 순서: ① 초안 행이 없으면 만들고 잠금(`for update`) → ② 같은 `client_request_id`의 기록이 있으면 **초안은 건드리지 않고** 그 기록을 그대로 반환 → ③ `expected_revision`이 다르면 충돌 응답 → ④ 기록 생성 → ⑤ 초안 초기화(`revision + 1`). 응답은 `status`(`ok` / 재요청이면 `duplicate` / 불일치면 `conflict`)와 기록 ID, 완료 시각, 새 `revision`을 담아 완료 직후 [복사]가 서버 시각으로 문구를 만든다. 저장 RPC와 완료 RPC의 충돌 응답은 모두 `server_revision`과 서버 초안(`server_draft`)을 함께 돌려준다. 완료 충돌 시 기록은 만들지 않고, 클라이언트는 응답의 서버 초안으로 충돌 다이얼로그를 띄운다("서버 내용"을 고르면 화면을 서버 초안으로 교체하고, "이 기기 내용"을 고르면 `server_revision` 기준으로 다시 저장한다).
- **RPC 응답 키 규칙**: RPC의 jsonb 응답은 DB 관례대로 snake_case(`status`, `revision`, `updated_at`, `server_revision`, `server_draft`, `log_id`, `patrolled_at`)로 돌려주고, 서버 초안은 `{revision, updated_at, standing, cafe_zone, drowsy, away, memo}` 평평한 형태다. 클라이언트의 Supabase 어댑터(`lib/patrol-draft-rpc.ts`)가 이를 camelCase TS 타입(`SaveDraftResult`·`CompletePatrolResult`, 서버 초안은 `PatrolDraft`의 `content` 중첩)으로 변환한다.
- 완료 요청에는 클라이언트가 만든 요청 ID(UUID)를 실어 보내고, 완료 버튼은 처리 중 비활성화한다.
- **방치된 초안 정리**: 주기 작업(`pg_cron`, 30분마다)이 마지막 저장으로부터 2시간 이상 지난 **비어 있지 않은** 초안을 **빈 값 + `revision + 1`로 초기화**한다(행 삭제 없음). 이미 빈 초안은 건드리지 않아 `revision`이 불필요하게 올라가지 않는다. 영업일 경계(04:00)를 넘겨 작성 중인 초안은 최근에 저장되므로 유지된다. 초안의 영업일 비교로 복원을 막지 않는다.

## 🕓 영업일 규칙

- 기록의 영업일은 **완료 시각** 기준이다: 04:00:00 이후는 당일, 03:59:59까지는 전일. 03:50에 작성을 시작해 04:10에 완료하면 04:10 기준 영업일에 기록된다.
- 영업일 계산은 DB 안(완료 RPC)이 기준이며, 계산식은 `private.business_date_of(timestamptz)` 함수로 분리해 완료 RPC와 경계값 검증에 함께 쓴다. TypeScript `lib/business-date.ts`는 화면 표시와 날짜 이동 기본값용이며 `Asia/Seoul`을 명시해 계산한다. SQL과 TS 모두 서버 기본 시간대에 의존하지 않는다.
- DB 기본 시간대는 한국(`Asia/Seoul`)으로 설정한다.
- 일지 조회의 기본 날짜(현재 영업일)는 서버에서 계산한다. Cache Components 환경이므로 현재 시각을 읽기 전에 `await io()`를 호출하고 `<Suspense>` 경계 안에서 `?date` 값을 해석한다 (`node_modules/next/dist/docs/01-app/03-api-reference/04-functions/io.md`).
- 경계값 확인표:

| 완료 시각 (KST) | 영업일      |
| --------------- | ----------- |
| 03:59:59        | 전일        |
| 04:00:00        | 당일        |
| 00:00:00 (자정) | 전일        |
| 월말 03:59:59   | 전일(말일)  |
| 월초 04:00:00   | 당일(1일)   |
| 연말 23:59:59   | 당일(12/31) |
| 1/1 03:59:59    | 전일(12/31) |

- 기존 스타터의 `username`(unique)·`website`·`avatar_url` 컬럼과 관련 제약은 쓰지 않으므로 정리한다(프로필 사진 기능은 MVP 범위 밖).

### 데이터 접근 규칙 (RLS)

모든 권한 판정은 DB에서 강제한다(화면에서 버튼을 숨기는 것은 편의일 뿐).

- profiles: 본인 행만 조회(본인 `role` 확인 가능). 앱 경로에서는 insert 불가, 본인 `full_name`만 수정 가능. **`role`은 앱에서 변경 불가**(Supabase 대시보드에서만). 비로그인 조회 불가(이름은 `staff_names`로만 공개). 컬럼 단위 제한은 행 정책이 아니라 **컬럼별 권한(GRANT)**으로 구현한다.
- staff_names: 누구나 조회. 앱에서 쓰기 불가(트리거만 갱신).
- patrol_logs: **누구나 조회**(비로그인 포함). 직접 insert 불가(완료 RPC로만 생성). 수정은 `(본인이면서 현재 매니저·관리자) 또는 관리자`만, `standing, cafe_zone, drowsy, away, memo` 컬럼만 가능(컬럼 권한). 삭제도 같은 조건. 완료 시각·영업일·작성자는 수정 불가. 값 검증(양의 정수, 카테고리 내 중복 없음, 메모 길이)은 DB 제약으로 강제한다.
- patrol_drafts: 본인 행만 조회. 쓰기는 `save_patrol_draft` / `complete_patrol` RPC로만.
- quick_tags: 비로그인은 활성 태그만, 로그인 사용자는 활성 태그만, 관리자는 전체(숨김 포함) 조회. 두 경우를 정책 두 개(비로그인용/로그인용)로 나눈다. 추가/수정/삭제와 순서 맞바꿈은 관리자만.
- **역할 판별 함수(`is_admin`, `is_staff`)**: API로 노출되지 않는 별도 스키마(`private`)에 두고, 로그인 사용자 권한으로 정책에서 호출되게 하되 외부에서 직접 호출할 수 없게 한다.
- **RPC 3종**: 기본 부여되는 실행 권한을 회수하고 로그인 사용자에게만 부여하며, **함수 본문 안에서** 호출자 역할(`is_staff`/`is_admin`)을 다시 검사한다(브라우저가 직접 호출해도 안전하도록).

### 구현 시 지켜야 할 기술 규칙

- **Cache Components**: 로그인 정보(쿠키)나 DB를 읽는 컴포넌트는 `<Suspense>` 경계 안에 두고 로딩 표시를 제공한다 (`node_modules/next/dist/docs/01-app/02-guides/authentication-with-cache-components.md`).
- **서버 권한 검증**: `lib/auth/dal.ts`의 `requireStaff()` / `requireAdmin()`이 로그인 정보와 `profiles.role`을 서버에서 확인하고 부족하면 리디렉션한다. 순찰 기록 페이지·퀵 태그 관리 페이지와 **모든 Server Action**에서 호출한다(레이아웃에서만 검사하지 않는다). `proxy.ts`는 로그인 여부만 판단하고 공개 경로에 `/logs*`를 추가한다. 최종 방어선은 RLS다.
- **로그인 후 이동**: 인증 콜백 기본 경로, Google 로그인 버튼, 이메일 가입 확인 링크, 로그인 폼의 이동 경로를 모두 `/logs`로 맞추고, 스타터 데모인 `/protected` 페이지와 `/`(스타터 홈)는 `/logs`로 리디렉션한다. 로그아웃 후에도 `/logs`로 이동하며 브라우저에 남은 `draft:` 백업 키를 모두 지운다.
- **원래 화면 복귀**: 비로그인이 작성 페이지로 보내질 때 원래 경로를 `next`로 전달하고, 로그인 폼·Google 버튼·인증 콜백이 같은 방식으로 이어받는다. `next`는 사이트 내부 경로만 허용하는 공통 검증 함수로 처리한다(외부 주소 리디렉션 방지).
- **이메일 가입 확인**: Supabase 확인 메일 템플릿을 `{{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&type=email&next=/logs`로 바꾸고(가입한 기기와 링크를 연 기기가 달라도 동작), `/auth/confirm` 라우트에도 `next` 검증을 추가해 기본값을 `/logs`로 한다.
- **시각 표시**: `HH:mm` 포맷은 서버·클라이언트 모두 `timeZone: 'Asia/Seoul'`을 명시한다(hydration 불일치 방지).
- **호출 경로**: 초안 저장·순찰 완료는 지연을 줄이기 위해 브라우저 Supabase 클라이언트에서 RPC를 직접 호출한다(실행 권한은 `authenticated`만, 역할 검사는 함수 본문). 기록 수정·삭제, 자리비움 처리, 퀵 태그 관리는 Server Action에서 `requireStaff()` / `requireAdmin()`을 호출하고 최종 판단은 RLS·컬럼 GRANT가 한다. 갱신·삭제된 행이 0개면 "권한이 없거나 삭제된 기록"으로 처리한다.
- **권한 미달 안내**: 서버 리디렉션은 `/logs?notice=<코드>`(`login-required` / `pending` / `admin-required`)로 전달하고 공통 배너가 문구를 표시한다. `requireStaff()`는 비로그인을 `/auth/login?next=<현재 경로>`로, `pending`을 `notice=pending`으로 보내며, `requireAdmin()`은 `manager`를 `notice=admin-required`로 보낸다. 알 수 없는 코드는 배너를 표시하지 않는다.
- **공통 모듈 위치**: `lib/auth/dal.ts`(`requireStaff` / `requireAdmin`, `getViewer`), `lib/auth/safe-next.ts`(내부 경로 검증), `lib/auth/notice.ts`, `lib/business-date.ts`, `lib/patrol-format.ts`, `lib/seat-numbers.ts`, `lib/quick-tag-label.ts`. 좌석·태그 문구 정규화는 클라이언트와 서버가 같은 함수를 쓰고 DB 제약과 규칙이 일치해야 한다.
- **검증 방식**: 테스트 러너는 도입하지 않는다(MVP 이후 검토). 순수 함수는 커밋하지 않는 임시 스크립트로, DB 권한·RPC는 Supabase MCP SQL로(역할을 흉내 낸 트랜잭션), 화면은 Playwright MCP로 확인한다.

## 📝 가정 사항

- 신규 가입자는 모두 `pending`이며 관리자 승격은 Supabase 대시보드에서 수동 처리한다. 승인 대기자가 쌓이면 운영 부담이 늘 수 있고, 역할 관리 화면은 MVP 이후로 미룬다.
- 일지 조회는 로그인 없이 공개된다. 순찰 기록(좌석 번호·메모·작성자 이름)이 외부에 노출될 수 있음을 운영상 수용한다.
- 퀵 태그 5종은 초기 데이터(seed)로 등록하며, 이후 추가·수정·삭제는 관리자 전용 퀵 태그 관리 페이지(F11)에서 한다. 태그는 메모에 텍스트로만 반영되므로 태그 수정·삭제가 과거 기록에 영향을 주지 않는다.
- 단일 지점 운영이며 좌석 수/번호 체계에 상한을 두지 않는다 (양의 정수만 검증). 서로 다른 카테고리에는 같은 번호를 넣을 수 있고, 자리비움 번호를 이동할 때 대상 카테고리에 이미 있으면 자리비움에서 제거만 한다.
- 영업일 계산과 시각 표시는 Asia/Seoul 고정이며, 날짜 유틸은 `lib/business-date.ts`로 통일한다. DB 기본 시간대도 한국으로 설정한다.
- 초안은 사용자당 1건이며 행은 삭제하지 않는다. 2시간 이상 방치된 비어 있지 않은 초안은 30분 주기 작업이 비운다(영업일 경계에서 작성 중인 순찰이 유실되지 않도록 04:00 일괄 삭제는 하지 않는다). 완료 시 기록 생성과 초안 초기화는 한 트랜잭션으로 처리한다.
- 여러 기기에서 동시에 편집하면 `revision` 충돌 시 사용자가 어느 쪽을 쓸지 선택한다.
- 스타터 잔재(`components/tutorial`, `hero`, `deploy-button` 등)는 신규 화면 구현 시 정리한다. 공개 경로 조건은 일지 조회(`/logs*`) 추가를 반영해 수정한다.
- `next`, `@supabase/ssr`, `@supabase/supabase-js`는 정확한 버전으로 고정하며 업그레이드는 의도적으로 진행한다.
- 구현 전 확인 항목: Google 가입자가 `full_name`을 가입 정보에 담아 오는지(현재 확인됨), `pg_cron` 확장 활성화 여부, `patrol_logs`에서 `staff_names`를 함께 불러오는 조회가 비로그인 키로 동작하는지, 인앱 브라우저에서 이메일 확인 링크가 동작하는지, iOS Safari·Android Chrome에서의 복사 동작은 실기기로 확인한다.
- 사용자를 삭제하지 않고 강등으로 운영한다(기록의 작성자 참조 유지). 같은 좌석 번호의 서로 다른 카테고리 동시 수정은 마지막 저장이 우선한다.
